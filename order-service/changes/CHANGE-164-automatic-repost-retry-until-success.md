# CHANGE-164 — automatic repost retries after safe unsuccessful attempts

Date2026-10-29; owner Yao Xiang on order-service/admin-ui-linking. User explicitly requests implementation of repeated automatic repost attempts until success. This is an Order-only recovery/selection fix under existing NTH4 automatic-repost and ADR-055/V16 delegated execution, not a new peer protocol, scheduler, feature activation or financial bypass. Existing CHANGE-159–163 changes remain intact.

## Failure and fix

The previous due-order SQL permanently excluded any original with AUTO_REPOST:<originalId>, including a pre-Credit timeout recorded as a no-effect rejection. The compensation-first journal also correctly makes a compensated command terminal; re-executing its key would hit Credit's saved rejection/fence rather than perform a fresh safe reservation.

Approved user intent is implemented as repeated independent attempts on later existing minute passes while the saved plan remains enabled/due/unexpired, unheld and unused. Retain the first legacy key and every immutable command/candidate/result. After a terminal rejection with FULLY_COMPENSATED and FAILED/COMPENSATED Credit step, create a fresh opaque AUTO_REPOST-prefixed key and candidate; do not reset/delete the prior journal or reuse its fenced Credit identity. A PENDING/uncertain/reconciling attempt blocks a successor until compensation is confirmed. Each new attempt rechecks the original refund, requester/suppliers, plan and locked original version. No original HTTP mutation is retried after possible Credit effect.

SQL selects eligible originals and blocks pending/unsafe/successful attempts. Failed plans sort by their last failure time so recently failed plans cannot permanently monopolize the100-item batch ahead of older due work. SQL selects only the latest matching automatic command (actor/order scoped, newest first, limit1), with the original row lock and existing unique pending-target constraint serializing concurrent timers/manual repost. Successful successor/link/plan-used/command outcome remain one transaction. Success or configured expiry stops later attempts; holds/deactivation/other pending work pause them. No maximum number of safe attempts is added. Finite HTTP/lease/publication safeguards remain unchanged, including retained FAILED publication requiring redrive and unresolved Credit reconciliation.

No migration, endpoint/body/topic/credential/env/deployment change or sibling production edit. Existing feature/security flags remain required. Compatibility: first AUTO_REPOST key is retained; new retry keys are opaque within the already reserved namespace. Credit already accepts opaque command keys/candidate IDs and new generations; no new API is assumed.

Sequence: [automatic repost retries](../docs/diagrams/automatic-repost-retries.mmd). Existing classes keep their responsibilities: scheduler selects/isolates jobs, coordinator registers and executes one attempt, store supplies bound latest/safe-outcome SQL, repository selects due originals, and existing compensation workflow/journal/outbox owns uncertainty. No new persistence model or worker is introduced.
